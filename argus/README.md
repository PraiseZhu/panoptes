# Argus

PraiseZhu 本人的 PR 合并后，Argus 自动在合并后的版本上跑测试；确认是这个 PR 带来的问题才提 issue，每天 09:00 用飞书机器人 Doki 发一份人话日报。部署在 Mac mini，后台低优先级运行。

## 做哪几种测试

跑的是各项目自己已有的自动测试（和线上 CI 同一套），不额外写测试。

| 测试 | 测什么 | Mivo 插件 | AKB2 | Cindy |
|---|---|:-:|:-:|:-:|
| 单元测试 | 函数、模块的行为对不对 | ✓ | ✓ | ✓ |
| 类型检查 | 代码之间传的数据格式对不对得上 | ✓ | | ✓ |
| 打包构建 | 能不能打出可发布的插件包 | ✓ | | |
| 数据库迁移校验 | 老用户数据能不能正常升级 | | | ✓ |
| 集成测试 | 模块拼起来、和 git 配合是否正常 | | | ✓ |
| 代码规范 | 写法是否符合项目约定 | ✓ | ✓ | |
| 项目守卫 | 日志、多语言文案、循环依赖、目录结构、术语和品牌用词、接口地址、设计清单、架构约定 | ✓ | | ✓ |
| 接口测试 | 进程内接口测试，加上真起服务逐条发请求核对（Mivo） | ✓ | ✓ | |
| 浏览器端到端 | 在 Ego Lite 无头实例里走一遍真实流程（Mivo：保存、重开、导出） | ✓ | | |
| 性能基准 | 仓里已有的性能测试和它自带的阈值 | ✓ | | |
| AI 补测 | 分诊说涉及、但现有测试覆盖不到的方面（边界、出错处理、状态切换、并发等），由 AI 按项目自己的测试框架补写 | ✓ | ✓ | |

另外，gpt-6-luna 会读改动，给出一句话总结、测试没覆盖到的风险和疑似问题。它只做提示，不决定通过或失败。

AI 补测的每个测试都要附一个「植入错误」：测试在当前代码上通过、植入错误后失败，才算有效，否则丢弃。AI 补测和性能基准还在试运行，它们发现的问题只记「拿不准，要你看」，不自动提 issue。

每个 PR 先分诊：和 CI 一致的检查每次都跑；接口测试、浏览器这类可选检查，只在 Jev 判断这次改动涉及或拿不准时才跑，跳过的写进日报附录。浏览器全程无头、独立配置目录、不开窗口；运行时如果弹出系统密码框，日报会要你处理。

Cindy 宿主里的真实使用（把插件装进 Cindy 再点一遍）明确不做。还不做：Windows 和 Linux 上的兼容性、安全扫描。

## 怎么运转

1. **发现 PR**：每 5 分钟扫一次登记的仓库，只收 PraiseZhu 本人合并的 PR；只改文档的直接跳过。
2. **隔离测试**：在 `sandbox-exec` 隔离目录里跑，测试进程读不到家目录、外接盘和凭证。一次只测一个 PR，磁盘剩余低于 12 GB 时暂停测试。
3. **三重确认**：有测试失败时，先换新环境重跑，再跑合并前的版本，最后跑最新主干，逐个失败用例对比。只有「这个 PR 引入、而且现在还在」的问题才算缺陷；拿不准就记「待核实」，不提 issue。
4. **提 issue**：统一发到私有仓 `PraiseZhu/pr-qa-agent-deploy`，先观察误报，约 2026-10-01 再决定要不要改回各自仓库。同一问题只开一条，再出现就在原 issue 下追加记录；修好关掉后又复发会重新打开；关闭时选了「不修」的不再提醒。
5. **日报**：每天 09:00 私聊发送。第一句先回答「今天要不要你处理」；每个 PR 标一个判定（已执行检查未见新问题 / 有问题要你处理 / 未完成验证 / 拿不准要你看）；issue 段写新提的和还没解决的（实时读 GitHub）；下一步只列要做的事；AI 的提示和猜测、老失败放附录；适用测试没覆盖、检查没跑成、补测无效会进入主结论，不能当作完整通过。分诊拿不准（灰区）且这次已经跑过有效检查时，不因此标成未完成验证，也不进【要做】。日报另列上海时间昨日的合并入账数，区分跑过测试、仅文档、未接入和尚未执行。范围仅限登记仓库的本人已合并 PR。Mivo 只改 `public/changelog.json` 时按只改文档跳过测试。

命名用例的“对照通过”需要结构化报告证明该用例确实执行并通过；跳过、待办、该版本没有此用例或缺少报告都记待核实。Mivo 的 Vitest 和金丝雀的 Node 测试已接入逐用例证据；尚未接入的测试步骤仍保留失败记录，但不能仅凭失败名单里没有某个名字就确认它通过。重跑或最新主干才出现的新失败也会留在待核实清单，不能被“只有老失败”或“已经修好”掩盖。新字段只随后续任务保存，不改写历史记录。

## 结论含义

| 结论 | 意思 |
|---|---|
| 通过 | 实际执行的检查通过；覆盖缺口另列，不能据此确认全部适用测试完成 |
| 无新问题 | 能核实的失败在合并前就存在；未知对照不算老失败，AI 失败补测不算覆盖 |
| 只改文档 | 没跑测试 |
| 发现问题 | 三重确认成立，已提 issue |
| 不稳定 | 第一次失败，重跑通过；原因待核实，不能排除产品间歇性问题 |
| 已被后续修复 | 最新主干已经好了 |
| 待核实 | 没法完全确认，交给人看 |
| 测试环境问题 | 依赖装不上或流程反复出错 |
| 暂时无法测试 | PR 的作者或合并状态对不上 |
| 未接入 | 项目还没配置测试 |
| 已过期 | 排队超过 30 天 |

## 安装（Mini）

前置条件：
- Node 24+
- 已登录的 `gh`
- 飞书 Doki 凭证
- 模型网关地址和 key
- GitHub App「Argus QA PraiseZhu」私钥（可选；没有时所有仓都走 `gh`）

步骤：
1. 生成凭证文件，权限 0600，绝不入 git：
   `printf 'ARGUS_LLM_BASE_URL=<地址>\nARGUS_LLM_API_KEY=<key>\n' | python3 scripts/assemble-secrets.py <Doki 目录> ~/Library/Application\ Support/PraiseZhu/pr-qa-agent/secrets.env <飞书姓名>`
2. （可选）把 App 私钥放到同一目录下的 `github-app.pem`，权限 0600；并在 `secrets.env` 里补上 `ARGUS_GH_APP_ID`、`ARGUS_GH_APP_INSTALLATION_ID`、`ARGUS_GH_APP_SLUG`、`ARGUS_GH_APP_KEY_FILE` 四项。
3. 安装或升级，固定到某个提交：`bash scripts/install-mini.sh <sha>`。通过 ssh 执行时，先把 `/opt/homebrew/bin` 加进 PATH。

安装后有两个后台服务：
- `com.praise.argus.control`：常驻，负责扫描、测试、提 issue；09:05 还没发出日报时补发。
- `com.praise.argus.daily`：每天 09:00 发日报。

## 常用命令（Mini）

| 命令 | 作用 |
|---|---|
| `argus status` | 心跳、队列、磁盘 |
| `argus runs` | 最近任务和结论 |
| `argus doctor` | 自检 GitHub、模型、飞书、磁盘 |
| `argus daily-report --dry-run` | 预览日报，不发送 |

日志在 `~/Library/Logs/PraiseZhu/pr-qa-agent/`。每次执行的证据保存在 runtime 的 `evidence/`，包含实际检出版本、测试配置摘要、执行命令模板及脱敏结果摘要。旧版证据无法补出的版本或断言，不会被事后伪造。已结束任务不会因后来接入测试而自动补跑。

## 目录（Mini）

- `~/Library/Application Support/PraiseZhu/pr-qa-agent/`：代码、账本、证据、凭证。**不能删**。
- `~/Library/Caches/PraiseZhu/pr-qa-agent/`：代码镜像和依赖缓存，超过 12 GB 会自动清理，可以重建。

## 接入新项目

1. 在 `config/registry.json` 登记仓库，填写 `repo`、`displayName` 和 `profile`。
2. 写 `config/profiles/<名字>.json`，包含：
   - `intentZh`：产品意图，给 AI 读；
   - `aPaths`：只改这些路径时视为文档改动；
   - `cPaths`：高风险路径；
   - `steps`：测试步骤，按顺序执行。每步的 `kind` 分三类：`setup` 准备环境，`product` 功能检查，`quality` 质量检查。

参照现有的几个 profile 写即可。
