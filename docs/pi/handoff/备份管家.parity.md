## C. 重置后能否全自动恢复（调研 + 提案，未安装）
**事实**：PID 1 是 `/tini -- /pod-daemon`，没有 systemd，也没有 rc.local；cron 是盒子上的普通进程，重置后 cron、rsync 包和 cron 进程都没了（10/19、10/21 13:07、10/22 12:34），所以 `@reboot` 和 /etc/cron.d 都不可靠（它们自己就在被删的那层）。/workspace 和 /home/box 都保留下来了。/cursor/stores 是平台挂载，按需挂载，不能当作开机钩子。唯一确定还会跑的是：agent 打开 shell 时会读 /home/box 下的 bash 启动文件（~/.bashrc）。
**提案**：在 ~/.bashrc 末尾加一行守卫：若 `/etc/cron.d/grokbot-box-sync` 不存在且 `pgrep -x cron` 为空 → 用 flock 后台跑 `restore.sh --dry-run > /workspace/grokbot-box-check/auto-<时间>.dry.log`，dry-run exit 0/2 才接着跑 `restore.sh --only 10` 和 `--only 20`（装包 + cron.d + 起 cron），然后手动跑一次 sync.sh --no-push 核对；其余段（密钥、bot、Cindy）留给人。
- 优点：不需要平台支持；系统层（最常丢）几分钟内回来，备份推送不断档；先 dry-run，日志可审。
- 缺点：要等第一个 agent 开 shell 才触发；bashrc 里跑 sudo apt 会拖慢那个 shell（放后台）；只覆盖系统层。
- 风险：重置是“半重置”时误判（已用“cron 文件和 cron 进程都没有”双条件）；多个 shell 并发（flock + 完成标记）；apt 卡住（已有 --force-conf*，加 timeout）；改 bashrc 影响所有 agent。
- 本次**没装**这个钩子：涉及 sudo apt 自动执行，属于要 Praise 拍板的改动。批准后我来加，并先在 `--dry-run` 模式跑一轮。
